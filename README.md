# chaos-proxy

Инструмент инъекции сетевых сбоев для тестирования отказоустойчивости систем на основе Apache Kafka.

Приложения, работающие с Kafka, в эксплуатации регулярно сталкиваются с недоступностью брокера, высокой задержкой сети, дублированием и повреждением сообщений, сменой лидера партиции. Как система поведёт себя в этих условиях (потеря данных, повторная обработка, некорректное восстановление соединения), аналитически не предсказать: обычно это выясняется постфактум, после реального инцидента.

chaos-proxy — прокси, который прозрачно встаёт между клиентским приложением и кластером Kafka. Приложение работает с Kafka как обычно и не знает о посреднике, а прокси по сценарию целенаправленно ломает трафик. Это позволяет воспроизводить отказы в контролируемой среде и количественно измерять реакцию системы.

## Чем отличается от toxiproxy

[Toxiproxy](https://github.com/Shopify/toxiproxy) работает на уровне TCP и не знает Kafka-протокола: он может оборвать соединение или добавить задержку, но не умеет «потерять ответ на конкретный Produce», «испортить запись с пересчётом CRC» или «подменить лидера партиции». chaos-proxy разбирает Kafka wire-протокол и ломает систему на уровне запросов, ответов и записей. Open-source инструментов с таким уровнем понимания протокола нет, есть только коммерческий Conduktor Gateway.

## Что умеет ломать

- **Соединение:** обрыв, задержка соединения с конкретным брокером.
- **Запрос и ответ:** задержка, байтовая порча, потеря запроса, **потеря ответа** (запрос дошёл до брокера, а клиент не получил ack). Именно потеря ack порождает реальные дубли у producer'а без идемпотентности и потери у at-most-once.
- **Записи:** дублирование и порча конкретных Kafka-записей, в том числе порча с пересчётом CRC (доходит до приложения, а не отсекается проверкой контрольной суммы).
- **Лидер партиции:** подмена лидера в ответе Metadata; клиент получит `NOT_LEADER_OR_FOLLOWER` и обновит метаданные. Прокси подменяет метаданные, но не запускает настоящие выборы лидера внутри кластера.

## Сценарии и воспроизводимость

Детерминированной делается сама инъекция, а не исход: поведение клиента (таймеры, батчинг) от прогона к прогону плавает. Поэтому:

- триггеры задаются **событиями протокола**, а не временем или вероятностью: «на 3-м Produce в партицию 0», «на батче с сообщением ID ≥ N», «на первом ответе OffsetCommit»;
- вероятностные правила работают от фиксированного seed;
- каждая инъекция пишется в журнал (соединение, API, correlation id, правило, действие), чтобы прогон можно было разобрать и повторить;
- интенсивность задаётся относительно таймаутов клиента (`request.timeout.ms`, `session.timeout.ms`, `delivery.timeout.ms`): сбой слабее таймаута ничего не покажет.

## Манифест сценария

Прокси запускается с YAML-манифестом, который целиком описывает прогон: какие брокеры проксировать и что ломать. Файл читается строго: неизвестное поле или действие — ошибка при старте, а не молча проигнорированное правило.

```yaml
seed: 42
log: injections.jsonl

brokers:                       # пара listen/upstream, она же таблица подмены адресов
  - { listen: ":19092", upstream: "kafka1:9092" }
  - { listen: ":19093", upstream: "kafka2:9092" }

rules:
  - name: lose-ack
    when: { api: Produce, nth: 3 }            # 3-й подходящий запрос
    do:   { drop_response: { close: true } }  # дошёл до брокера, ack не вернулся

  - name: slow-kafka2
    when: { broker: "kafka2:9092", after: 10s }
    do:   { delay: { duration: 5s, jitter: 1s } }

  - name: dup-message
    when: { api: Produce, message_id_gte: 50000 }
    do:   { duplicate_request: {} }
```

Правило состоит из `when` (триггер и фильтр), `do` (действие) и необязательного `times`.

- **Триггеры:** `nth`, `after`, `message_id_gte`, `probability` (от `seed`).
- **Действия:** `reset_connection`, `delay`, `drop_request`, `drop_response`, `corrupt_bytes`, `duplicate_request`, `corrupt_record`, `fake_leader`.
- **Фильтры:** по `api` и `broker` работают без разбора тела запроса; по `topic`, `partition` и `message_id` нужен декод тела, поэтому они появятся в M3. Манифест с ещё не поддерживаемым полем отвергается с понятной ошибкой.

Манифест описывает только прокси. Нагрузку, стратегии обработки и проверку потерь и дублей запускает отдельный стенд, который сам генерирует манифест на каждый прогон.

## Архитектура

Два слоя:

1. **TCP passthrough** — приём соединений и двунаправленная пересылка байт.
2. **Kafka-protocol-aware слой** — разбор границ фреймов (length-prefix) и заголовка запроса (`api_key`, `api_version`, `correlation_id`), сопоставление каждого ответа с запросом. Тела сообщений декодируются через пакет `protocol` из [segmentio/kafka-go](https://github.com/segmentio/kafka-go) только для тех фреймов, которые нужно изменить; остальное пересылается как есть.

### Как весь трафик попадает в прокси

Клиент использует bootstrap-адрес только для первого подключения, дальше ходит к брокерам напрямую по адресам из ответа Metadata. Поэтому прокси переписывает host/port брокеров в ответах Metadata и FindCoordinator на собственные адреса (отдельный listener на каждый брокер); таблицей подмены служит секция `brokers` манифеста. Тот же механизм нужен для подмены лидера.

Альтернатива — выставить `advertised.listeners` брокеров на адреса прокси.

### Границы

- Только PLAINTEXT: TLS и SASL не поддерживаются, инструмент для тестового окружения.
- Трафик между брокерами через прокси не идёт, репликацию ломать нельзя.
- Современные клиенты согласуют версии API новее тех, что декодирует `kafka-go/protocol`; для семантических сбоев прокси будет ограничивать версии в ответе ApiVersions.

## План

| Этап | Что делаем |
|---|---|
| M0 | Прозрачный TCP passthrough, разбор границ фреймов, сопоставление ответов с запросами, хук подмены ответов; YAML-манифест (пока только `brokers`) |
| M1 | Обрыв / задержка соединения к брокеру; секция `rules`, фильтры `broker` и `after` |
| M2 | Уровень запроса: задержка, байтовая порча, потеря запроса, **потеря ответа (ack)**; триггер `nth`, фильтр `api` |
| M3 | Семантический хаос: фильтры по topic / partition, триггер `message_id_gte`, дублирование / порча записей (с пересчётом CRC), подмена лидера в Metadata, ограничение версий в ApiVersions |
| M4 | Журнал инъекций, `probability` и `seed`, проверки манифеста; HTTP control API только если понадобится стенду |

Статус: M0 в работе.

## Эксперименты

С помощью прокси планируется сравнить, как стратегии обработки сообщений ведут себя под сбоями:

- at-most-once;
- at-least-once + retry;
- идемпотентный consumer;
- exactly-once через Kafka-транзакции.

Метрики: потери и дубли для каждой комбинации «стратегия × тип сбоя», плюс время восстановления. Каждое сообщение несёт уникальный монотонный ID, по которому считаются потери и дубли; нагрузка фиксирована (~100k сообщений), на каждую комбинацию 5–10 прогонов. Нагрузка, проверка и сами стратегии — отдельный стенд вне прокси; падения процесса consumer'а он делает сам, прокси их не вызывает.
